# 大口九：多摄像头、规则全局配置与多音箱设计

## 背景

当前 MVP 只读取一个 `STREAM_URL`，只维护一套人员状态和欢迎规则，并把所有播报发送到一个
`MI_DID`。欢迎词写死在代码中，管理页只能开启或关闭唯一的全局规则。

本次迭代将应用扩展为：

- 从 `go2rtc` 发现并接入多个摄像头；
- 每台摄像头独立开启或关闭内置规则；
- 欢迎规则使用一份可在管理页编辑的全局欢迎词列表；
- 在环境配置中声明多个小爱音箱，每台摄像头固定配对一个音箱；
- 在低配置服务器上共享昂贵资源，并在无规则启用时释放不必要的资源。

部署前由用户清空旧数据库。本次不实现旧 schema 迁移，也不兼容单个 `MI_DID`。

## 目标

1. 应用启动时和用户手动刷新时读取 `go2rtc /api/streams`，发现任意数量的码流。
2. 新发现摄像头默认关闭所有规则，并默认配对音箱配置数组中的第一项。
3. 每台摄像头独立维护规则开关、人员状态、冷却状态、运行状态和音箱配对。
4. 所有摄像头共享一个人员检测模型和公平调度器。
5. 欢迎词列表由所有摄像头共享，页面保存后立即对新事件生效。
6. 同一个音箱上的播报串行执行，不同音箱可以并行执行。
7. 没有启用视觉规则的摄像头不启动 FFmpeg；没有任何摄像头启用规则时不加载检测模型。
8. 同时启用四台或更多摄像头时显示资源提示，但不阻止用户继续启用。
9. 保持单页、无家庭成员区分、无登录的局域网管理体验。

## 非目标

- 不做动态插件加载或通用动态规则表单。
- 不在管理页添加、删除或编辑 `go2rtc` 码流。
- 不允许在管理页修改摄像头名称、音箱 DID 或小米账号。
- 不自动轮询 `go2rtc` 发现新设备。
- 不自动探测音箱，不自动判断不同音箱型号的 MIoT 播报能力。
- 不在配对音箱失败时回退到其他音箱。
- 不兼容旧数据库 schema，不读取或迁移旧规则和事件。
- 不兼容 `MI_DID`。
- 不新增截图、录像、音频文件、人物身份识别或云端视觉分析。
- 不实现粤语、音乐播放或动物识别规则。

## 总体架构

应用继续使用单个 Python 进程和一个 FastAPI worker：

```text
go2rtc /api/streams
        |
        | 启动时一次 + 页面手动刷新
        v
设备编排器 ---- SQLite 状态存储 ---- 管理页面
    |
    +-- 摄像头 A 执行单元 -- 最新帧 --+
    +-- 摄像头 B 执行单元 -- 最新帧 --+--> 共享检测调度器 --> 共享 ONNX 模型
    +-- 摄像头 N 执行单元 -- 最新帧 --+
                                               |
                                               v
                                  逐摄像头人员状态与规则实例
                                               |
                                               v
                                      带目标音箱的播报动作
                                               |
                        +----------------------+----------------------+
                        v                                             v
                  音箱 A 串行队列                              音箱 B 串行队列
                        |                                             |
                        +---------------- MiService ------------------+
```

设备编排器拥有发现状态、摄像头执行单元、共享检测调度器和音箱管理器。Web 模块只通过小型
接口读取快照和提交命令，不直接管理线程、FFmpeg 或 ONNX 对象。

## 环境配置

保留以下全局凭据：

- `MI_USER`
- `MI_PASS`

新增必填的 `MI_SPEAKERS_JSON`，使用 JSON 数组而不是自定义分隔字符串。例如：

```dotenv
MI_SPEAKERS_JSON='[{"id":"living_room","name":"客厅音箱","did":"123456789"},{"id":"bedroom","name":"卧室音箱","did":"987654321"}]'
```

每项字段：

- `id`：应用内稳定 ID，1 到 64 个小写字母、数字、下划线或连字符；必须唯一；写入数据库和
  事件记录。
- `name`：页面显示名称，去除首尾空白后为 1 到 50 个字符。
- `did`：MiService 使用的设备 DID，必须是非空字符串；只保留在进程内，不写入数据库、页面
  或日志。

数组不能为空，第一项是新摄像头的默认音箱。配置无效时应用拒绝启动并给出不包含凭据的分类
错误。`MI_DID` 不再读取；只配置 `MI_DID` 时应用启动失败。

新增：

- `GO2RTC_API_URL`，默认 `http://127.0.0.1:1984`。
- `GO2RTC_RTSP_BASE_URL`，默认 `rtsp://127.0.0.1:8554`。

应用对码流名称进行 URL 路径编码后构造 RTSP 地址，不把 `/api/streams` 返回的名称直接拼接
进命令或 shell。现有模型、检测帧率、置信度、离开时间、冷却时间和 Web 参数继续作为全局
环境配置。

## 数据模型

继续使用 Python 标准库 `sqlite3` 和原路径：

```text
/var/lib/daihougou/data/daihougou.db
```

SQLite 不启动独立服务。它在一个文件内提供原子提交、并发访问协调、唯一性约束和有界事件
查询。应用不引入 ORM，也不增加第三方数据库依赖。

数据库使用新的 schema，并设置新的 `PRAGMA user_version`。如果发现不兼容的旧 schema，应用
拒绝运行并提示按 runbook 重置数据库，绝不静默删除用户文件。

### `cameras`

```text
stream_id       TEXT PRIMARY KEY
speaker_id      TEXT NOT NULL
first_seen_at   TEXT NOT NULL
last_seen_at    TEXT NOT NULL
```

`stream_id` 就是 `go2rtc` 码流名称，同时也是页面显示名称。码流改名视为新摄像头。旧名称对应
的记录保留；在一次成功刷新中未出现时标记为不可用，但不删除规则和配对。

`speaker_id` 只引用环境配置中的稳定音箱 ID，不对 DID 建立数据库关系。若该 ID 不再出现在
环境配置中，摄像头进入“需要重新选择音箱”状态，不自动改绑。

### `camera_rules`

```text
camera_id       TEXT NOT NULL REFERENCES cameras(stream_id)
rule_id         TEXT NOT NULL
enabled         INTEGER NOT NULL CHECK (enabled IN (0, 1))
updated_at      TEXT NOT NULL
PRIMARY KEY (camera_id, rule_id)
```

每个新摄像头都会创建一条关闭的 `welcome_on_person_entry` 规则实例。规则开关不再存放在全局
`rules` 表中。

### `rule_configs`

```text
rule_id         TEXT PRIMARY KEY
config_json     TEXT NOT NULL
updated_at      TEXT NOT NULL
```

欢迎规则的配置格式为：

```json
{"phrases":["你好呀，欢迎回来。","嗨，很高兴见到你。"]}
```

新数据库使用当前三条内置欢迎词初始化。配置必须包含 1 到 20 条欢迎词；每条去除首尾空白后
为 1 到 100 个字符。空行忽略，重复项按首次出现顺序去重。校验失败时不修改已有配置。

### `events`

在现有事件信息基础上增加：

```text
camera_id       TEXT NULL
speaker_id      TEXT NULL
```

事件仍最多保留 5000 条，并只记录分类状态、耗时、摄像头 ID、非敏感音箱 ID 和脱敏详情。不
记录帧、码流 URL、DID、账号、密码、Token、Cookie 或小米原始响应。

### 存储模块接口

存储模块隐藏建表、事务、JSON 编解码、锁和事件裁剪。调用方只需要以下能力：

- 同步一次发现结果，并为新摄像头创建默认关闭的规则和默认音箱配对；
- 列出摄像头配置；
- 读取和更新某台摄像头的规则开关；
- 读取和更新某台摄像头的音箱配对；
- 读取和原子更新某类规则的全局配置；
- 写入和查询有界事件；
- 查询某台摄像头某条规则最近一次触发结果。

运行时和 Web 测试使用满足相同小接口的内存实现；不为了假想的其他数据库暴露 SQL 或通用
查询接口。

## 摄像头发现

应用只在两个时机请求 `GET {GO2RTC_API_URL}/api/streams`：

1. 应用启动时一次；
2. 用户点击管理页“刷新摄像头”时一次。

没有后台发现轮询。请求使用短超时，要求 JSON 对象响应，并把对象顶层键作为码流名称。一次
成功发现会：

- 更新已出现摄像头的 `last_seen_at`；
- 为新名称创建摄像头记录、默认音箱配对和关闭的欢迎规则；
- 在当前运行快照中把未出现的旧名称标记为不可用；
- 按最新可用性启动或停止相关摄像头执行单元。

发现失败时：

- 不修改数据库中的摄像头、规则或配对；
- 保留上一次成功发现的可用性快照；
- 不停止已经运行的执行单元；
- 在页面显示分类错误并允许再次手动刷新。

启动发现失败且没有当前进程内成功快照时，持久化摄像头显示为“发现状态未知”。真实 FFmpeg
拉流结果仍可以独立报告运行状态。

## 摄像头执行单元

每台摄像头拥有独立执行单元，负责：

- 一个按需启动的 `FfmpegFrameSource`；
- 只保留最新帧；
- 独立的 `PresenceTracker`；
- 独立的欢迎规则冷却状态；
- 拉流、检测、画面和最后错误快照。

只有同时满足以下条件时才启动执行单元：

- 至少一条视觉规则已开启；
- 最近一次成功发现中该码流可用，或尚无成功发现结果但它是已保存的启用摄像头；
- 应用未停止。

关闭最后一条视觉规则，或一次成功刷新确认码流已被删除时，停止对应 FFmpeg 并清空待检测帧。
物理摄像头离线但码流仍存在于 `go2rtc` 时，执行单元保持监督和自动恢复；连续无帧后只降级
该摄像头，不推动“无人”状态，也不误触发欢迎。

摄像头重新启动或规则从关闭变为开启时，人员状态从未知开始校准。画面已经有人时不会立即
产生进入事件；必须先观察到稳定无人，再观察到有人。

## 共享检测调度器

所有启用摄像头共享一个 `PersonDetector` 和 ONNX session。检测器串行调用，避免同时运行多个
模型实例或对同一 session 进行不可控并发。

调度器为每台摄像头最多保留一个“有新帧”标记，并按轮转顺序选择摄像头。取得任务时读取该
摄像头当时的最新帧。因此检测速度低于总输入速度时只丢弃旧帧，不建立无界队列，也不会让一
台高帧率摄像头长期饿死其他摄像头。

第一台摄像头启用视觉规则时加载模型并启动调度器。最后一台摄像头关闭视觉规则后停止调度器、
关闭所有帧源并释放模型引用。再次启用时允许重新加载模型，页面在加载期间显示“启动中”。

单帧或单路解码失败只降级对应摄像头。模型加载失败或连续的系统性推理错误会把共享检测器
标记为降级；Web 和配置管理保持可用。

## 规则实例与全局配置

规则类型仍是代码内置的 `welcome_on_person_entry`，不做动态插件加载。每台摄像头拥有独立的
规则实例，因此以下状态都按摄像头隔离：

- 开关；
- 人员进入事件；
- 上次动作时间与冷却；
- 最近一次触发结果。

欢迎词列表是规则类型的全局配置。产生 `person_entered` 时，规则读取当时最新的已校验列表并
随机选择一条。页面保存后无需重启；已经进入音箱队列的动作保留选择时的文本，不被后续修改。

播报动作包含：

- `camera_id`；
- `rule_id`；
- `speaker_id`；
- `text`；
- 创建时间。

动作提交前要求摄像头仍有有效音箱配对。音箱消费者真正播报前再次检查：

- 该摄像头的该规则仍开启；
- 摄像头当前配对仍等于动作中的 `speaker_id`。

任一条件不满足就丢弃动作并记录分类事件，避免关闭规则或改绑后播放过期内容。

## 多音箱调度

音箱管理器从 `MI_SPEAKERS_JSON` 构造以稳定 ID 索引的音箱适配器。每个配置音箱拥有一个有界
异步队列和一个消费者：

- 同一音箱上的动作严格串行；
- 不同音箱的消费者可并行调用 MiService；
- 队列满时丢弃最新动作并记录事件，不阻塞检测；
- 播报失败不自动重试，避免恢复后播放过期欢迎；
- 目标音箱不可用时不改绑、不回退到默认音箱。

所有音箱共用同一个小米账号和持久 Token。任一调用确认需要重新认证时，音箱管理器进入全局
`reauth_required` 状态，拒绝所有新动作，并在页面显示统一认证错误。完成 runbook 中的交互式
认证并重启应用后恢复。

首版假设所有显式配置的音箱支持已验证的 `siid=5, aiid=3` 文本播报动作。不同型号兼容性由
用户先通过 PoC 验证；应用只报告调用失败，不自动改用其他 MIoT 动作。

## 管理页面

继续使用 Jinja2 服务端渲染和现有 CSS，不引入前端框架。页面保持全宽分区，不使用嵌套卡片。

### 状态摘要

显示：

- 应用状态；
- `go2rtc` 最近一次发现状态；
- 共享检测器状态；
- 小米账号认证状态；
- 已发现、已启用和已就绪摄像头数量。

没有摄像头启用规则时属于正常空闲状态。只有已启用摄像头无法工作或共享关键模块失败时才
降级。

### 全局规则配置

“人员进入欢迎”提供多行文本框，每行一条欢迎词和明确的保存按钮。提交后在服务端执行完整
校验：

- 成功时原子替换整个列表并提交后重定向；
- 失败时不写入，返回原页面并在输入框附近显示简短错误。

### 摄像头列表

每行显示：

- `go2rtc` 码流名称；
- 发现可用性、拉流、检测和画面状态；
- 欢迎规则开关；
- 配对音箱下拉框，只显示音箱名称；
- 最近一次欢迎触发结果。

摄像头名称不可编辑。页面提供“刷新摄像头”命令按钮。规则开关和音箱选择分别提交，不让一
项校验失败覆盖另一项设置。

当欢迎规则已开启的摄像头达到四台或更多时，在列表顶部显示简洁资源提示。提示不禁用开关，
也不改变健康状态。

### 最近记录

最近事件表增加摄像头和音箱两列；没有关联设备的全局事件显示空值。页面只显示稳定 ID 或
环境配置中的显示名称，不显示 DID。

## Web 命令与安全

保留 `GET /` 和 `GET /healthz`。增加服务端表单命令：

- 手动刷新摄像头；
- 更新指定摄像头的欢迎规则开关；
- 更新指定摄像头的音箱配对；
- 更新欢迎规则全局配置。

摄像头 ID 和规则 ID放在隐藏表单字段中，不放进 URL 路径，避免特殊码流名称影响路由解析。
所有写操作继续验证：

- 请求 `Origin` 与当前 `Host` 相同；
- HttpOnly、SameSite Strict Cookie 中的 CSRF Token；
- 表单中的 CSRF Token；
- 摄像头、规则、动作和音箱 ID存在于服务端当前数据中。

管理页仍无账号认证，只允许部署在可信局域网，不得暴露管理、go2rtc 或 RTSP 端口到互联网。
模板默认转义欢迎词和设备名称。

## 健康状态

`GET /healthz` 返回非敏感 JSON：

- 聚合 `status`；
- 应用、数据库、发现、检测器和音箱认证状态；
- 已保存、当前发现、已启用和已就绪摄像头数量；
- 每台摄像头的码流 ID、规则开关、发现、拉流、检测、画面和最后分类错误状态。

健康检查不返回欢迎词、DID、URL、账号或任何小米响应。无启用规则时返回健康；发现接口失败
但已运行摄像头继续工作时返回降级信息而不触发反复容器重启。只有进程关键后台任务终止、
数据库不可用或共享检测器不可恢复失败时返回不健康。

## 错误处理

- `go2rtc` 刷新超时或返回非法 JSON：保留旧清单和运行单元，页面显示发现失败。
- 新摄像头默认配置写入失败：整次同步回滚，不出现只有摄像头没有规则的半配置。
- 欢迎词校验失败：保留旧列表并显示字段错误。
- 配对音箱从环境中消失：停止向它提交新动作，页面要求重新选择，不自动改绑。
- FFmpeg 无帧：对应人员状态失效，30 秒后摄像头降级，自动监督恢复，不产生离开或进入事件。
- 单次检测异常：只记录对应摄像头失败；连续系统性失败时共享检测器降级。
- 音箱队列满、调用超时或响应失败：记录一次失败，不阻塞检测、不重试、不回退。
- 认证失效：全局停止接受播报，保留检测和管理能力。
- 停机：先停止接收新帧和规则动作，再停止检测器，最后在有限时间内结束各音箱消费者和
  FFmpeg；超时任务被取消并记录分类错误。

### 真实设备验收

## 验收标准

- 任意数量的 `go2rtc` 码流可以被保存并显示，新码流默认关闭规则。
- 每台摄像头规则、人员状态、冷却和音箱配对互不影响。
- 所有摄像头只加载一个人员检测模型，并在全部禁用时停止拉流和释放模型。
- 欢迎词可以在页面编辑，保存后立即用于新触发事件。
- 新摄像头默认使用音箱数组第一项；显式配对后固定使用目标音箱，失败时绝不回退。
- 同音箱播报串行，不同音箱可并行；过期动作在执行前被丢弃。
- 手动刷新之外没有设备发现轮询。
- 四路及以上显示提示但不限制启用数量。
- 页面、数据库和日志不暴露 DID、账号、密码、Token、Cookie 或完整设备响应。
- 自动测试、容器测试和上述真实设备验收均通过，README 与 runbook 与实际行为一致。
